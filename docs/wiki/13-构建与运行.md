## 1. 工程与环境

内置 Qwen3.5-2B 的 MLX 依赖需要 Xcode 的 Metal Toolchain。若编译器报告缺少该组件，在 Xcode 的 Settings → Components 安装，或使用 xcodebuild -downloadComponent MetalToolchain 下载。应用用户无需安装开发工具。

[project.yml](../../project.yml) 是 XcodeGen 配置源：`deploymentTarget`、`SWIFT_VERSION`、`xcodeVersion`、targets、签名与依赖均以它为准。
当前声明 macOS 15 最低部署、Swift 6 语言模式和 Xcode 27 工程版本；构建工具链还需包含源码引用的新 SDK API。
最低应用运行版本不等于开发机最低版本；不要沿用旧文档“macOS 13 + Xcode 16 即可构建”的假设。

`Memozia`、`MemoziaTests`（Swift Testing 单元测试）与 `MemoziaUITests`（XCUITest）均为 macOS target（工程已取消 iOS 支持，iOS 分享扩展 target 与相关代码已删除）。

### 应用显示名称

应用文件名与系统显示名统一为英文 `Memozia`。`project.yml` 的 `PRODUCT_NAME`、`INFOPLIST_KEY_CFBundleDisplayName` 与 `InfoPlist.xcstrings` 的 `CFBundleName` / `CFBundleDisplayName` 必须一致；不能让简体或繁体本地化把 Finder、Dock 名称覆盖为其他品牌名。打包后检查最终 `.app` 的基础 Info.plist 及各语言 InfoPlist.strings，而不只核对源码配置。


## 2. 构建与测试命令

在项目目录运行；若 Xcode 安装位置不同，替换 `DEVELOPER_DIR`。这也避免 `xcode-select` 指向 Command Line Tools 时找不到完整 SDK。

```sh
# 首次生成，或源文件增删、依赖/工程配置变化后运行；仅改文档不用执行
xcodegen generate

# macOS Debug
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project Memozia.xcodeproj -scheme Memozia -configuration Debug -destination 'platform=macOS' build

# Swift Testing（单元测试；UI 测试需 GUI 会话与辅助功能授权，见 §5）
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project Memozia.xcodeproj -scheme Memozia -configuration Debug -destination 'platform=macOS' test -only-testing:MemoziaTests

# XCUITest（冒烟 + 无障碍审计 + 多语言/RTL/伪本地化截图基线）
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project Memozia.xcodeproj -scheme Memozia -configuration Debug -destination 'platform=macOS' test -only-testing:MemoziaUITests
```

不要手改生成的 `.xcodeproj`。签名团队不可用时按本机环境配置后重生成工程。
测试 target 的 `TEST_HOST` 在 `project.yml` 中显式指向 app 内部可执行文件（`Contents/MacOS`），勿改回缺少该路径的旧值。
改了 `Scripts/` 下的构建脚本后必须重新执行 `xcodegen generate`：脚本内容在生成阶段写进工程，否则构建仍跑旧副本。

## 3. 模型与首次运行

- 首启同意隐私政策后直接进入主窗口。「帮助 → 首次使用指引」提供当前模式的完整教程。需要本机模型时再询问下载，麦克风、系统录音、语音识别、屏幕录制、辅助功能和提醒事项在使用相应功能时请求。
- 系统语音识别通过 `SystemTranscription` / `SystemTranscriptionService` 在 macOS 26+ 使用 SpeechAnalyzer；语言资产由系统按需管理，不依赖 Whisper 模型目录。`STTMode.defaultMode` 与体验模式解析器按系统能力决定默认引擎，旧系统保留 WhisperKit 路径。
- 本地 Whisper 通过设置选择模型文件夹，默认目录由 `WhisperModelFolder.defaultPath` 提供；模型与 tokenizer 文件须完整，加载逻辑会解析子目录。
- 设置页「下载模型」可按档位下载（`WhisperModelOption.catalog`），源可选 HuggingFace 官方或 HF-Mirror 镜像（默认镜像，见 `WhisperModelSource`）；下载走 `WhisperKit.download` 并显式传 endpoint，完成后从 `<模型文件夹>/models/<repo>/<档位>` 重命名到 `<模型文件夹>/<档位>`，随即加载该模型。下载任务经全局处理队列（`TaskCenter.whisperDownloadJob`），是**唯一支持真正暂停 / 续传**的任务：取消（含暂停触发的取消）保留已落盘分片与 `.cache` 元数据，继续时重新调度该步即从断点续传。
- 当前工程排除 `Resources/Models/**`，不要假设 App 内置 tiny/base/small/medium；模型只能由用户手动放置或经上述下载获得。
- 说话人分离模型由设置页下载，或指定包含 segmentation.onnx / embedding.onnx 的目录。下载与 Whisper 统一为「取消保留、重下续传」：`SpeakerDiarizationService.downloadFile` 用 URLSession 流式写临时文件，取消时把 `resumeData` 落盘为 `.resume`，重下时以 `downloadTask(withResumeData:)` 从断点继续。
- LLM 设置使用 OpenAI 兼容服务；请求端沿用 URL 校验，回环 HTTP 豁免与任意局域网 HTTP 是不同情况。

## 4. 脚本与资源

| 脚本 | 用途 |
|---|---|
| [fix_onnxruntime_framework.sh](../../Scripts/fix_onnxruntime_framework.sh) | scheme build pre-action 和 target preBuild 准备 ONNX Runtime 布局并安装 Sherpa no-TTS 构建 |
| [verify_embedded_frameworks.sh](../../Scripts/verify_embedded_frameworks.sh) | postBuild 校验 App 与 Xcode Run/Test 副本的 Sherpa 版本和动态库引用，再重签并校验签名 |
| [bump_build_number.sh](../../Scripts/bump_build_number.sh) | 发布前手动分配构建号，不在构建阶段运行 |
| [bump_version.sh](../../Scripts/bump_version.sh) | 发布时手动 `patch` / `minor` / `major` 更新营销版本，之后重生成工程 |

**ONNX Runtime 产物修复与校验**（启动崩溃防线）：

- 上游 ONNX Runtime framework 包含需规范化的实体目录，Sherpa 动态库也需改用应用包中 ONNX Runtime framework 的路径，两处调整分别保证签名与启动加载。
- [install_sherpa_no_tts.sh](../../Scripts/install_sherpa_no_tts.sh) 使用同版本官方 no-TTS macOS 构建的 C API 动态库，移除上游 SwiftPM 二进制静态编入的 eSpeak NG。首次准备时下载约 17 MB 归档并核对锁定的 SHA-256，随后从本次 SwiftPM 缓存复用。离线构建可将已下载的归档路径设为 `MEMOZIA_SHERPA_NO_TTS_ARCHIVE`。
- `Versions/Current` 为实体目录还会在 Xcode 生成构建计划时触发 `Couldn't resolve framework symlink`，早于 target preBuild。`Memozia` scheme 的 build pre-action 因此先运行同一幂等修复脚本；保留 target 阶段兜底，文件操作失败立即报错。命令行也应使用 `-scheme Memozia`。
- 修复脚本只定位**本次构建**的产物：`BUILD_DIR` / `BUILD_ROOT` 都是 `…/DerivedData/<工程>/Build/Products`（不含配置目录），`SourcePackages/artifacts` 位于其上级目录（`../../`）；另支持发布脚本显式传入的 `MEMOZIA_PACKAGE_CACHE_PATH`、`OBJROOT` 与仓库内 `.packages`（自定义 packageCachePath）。它不再遍历其他工程的 DerivedData；`install_name_tool` 修复失败会直接让构建失败。
- SwiftPM 会同时生成 `$(CONFIGURATION_BUILD_DIR)` 副本与 App 嵌入副本。Xcode Run/Test 会通过 `DYLD_LIBRARY_PATH` 优先加载前者；`install_name_tool` 又会使上游签名失效，因此 postBuild 需用与 App 一致的身份重签构建目录副本。校验脚本同时检查两处的引用与签名，防止「构建成功、调试或测试启动即被 AMFI 终止」。
- `Memozia` target 明确关闭 `ENABLE_USER_SCRIPT_SANDBOXING`：上述脚本必须修改 SwiftPM 动态 hash 路径下的二进制产物，并让 `codesign` 递归读取 framework 及其扩展属性，无法用固定的 Run Script Input/Output 列表完整声明。该设置只影响构建脚本的执行沙箱，不会关闭 App Hardened Runtime 或最终代码签名。

`Scripts/add_*l10n*.py` 属一次性本地化维护工具，不是正常构建必需步骤。
`Scripts/fill_empty_l10n.py` 用于补齐 `Localizable.xcstrings` 的空条目：静态解析各 `add_*l10n*.py` 的 `add(源文, [20 语言])` 取值（**不执行**它们，部分脚本无 `__main__` 守卫、导入即写文件），只写当前缺少译文的键与缺失的 zh-Hans 源文条目，已有译文一律不覆盖；写入前校验占位符种类/数量与源文一致，并列出仍未覆盖的键。
用户文案位于 `Localizable.xcstrings`；语言列表由 `knownRegions` 和实际资源决定。修改占位符需核对各语言类型。
图标尺寸生成前核查当前源图路径及 Assets 引用，不依赖旧文档中的 `icon.png` 假设。
应用图标使用 `Memozia/Resources/AppIcon.icon` 的原生 Icon Composer 资源，避免新系统对旧格式图标追加灰色容器；`Assets.xcassets/Logo.imageset` 用于设置页。排查图标时同时检查 Icon Composer 渲染和实际应用的系统图标，不能只检查 PNG 或 `.icns`。资源更新需同步 `AppIcon.icon/Assets/Artwork.png`，并由 Xcode 生成旧系统回退图标；参见 [Apple 文档](https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer)。

## 5. 测试覆盖与验证边界

- [MemoziaTests.swift](../../MemoziaTests/MemoziaTests.swift)：时长、状态/配置、导入与视频命名、关键帧指纹与事件/名额纯函数、导出文档等。
- [KeyframeExtractorTests.swift](../../MemoziaTests/KeyframeExtractorTests.swift)：代表帧跨时间窗判重与名额回填、`LLMService.visualChunks` 分段送帧（与上一行的分工：本文件只测这两个不变式）。
- [StabilityRegressionTests.swift](../../MemoziaTests/StabilityRegressionTests.swift)：看门狗、可取消门闸、流式合批、超时预算、磁盘节拍、临时目录唯一性、失败报告、词典扫描等。
- [WhisperModelDownloadTests.swift](../../MemoziaTests/WhisperModelDownloadTests.swift)：模型档位名（glob 唯一性/精确仓库目录名）、下载源端点与默认值、`HF_ENDPOINT` 写入、三件套就绪判定与档位隔离（均为纯逻辑，不联网）。
- [LLMTitleGenerationTests.swift](../../MemoziaTests/LLMTitleGenerationTests.swift)：本地标题的能力协商、流式/完整 JSON 兼容、思考隔离、断流、超时与取消；默认仅离线测试。真实本地服务验证需设置 `TEST_RUNNER_MEMOZIA_VERIFY_LOCAL_TITLE=1`、`TEST_RUNNER_MEMOZIA_LOCAL_TITLE_URL`（本地 Base URL）和 `TEST_RUNNER_MEMOZIA_LOCAL_TITLE_MODEL`（模型 ID），并用 `-only-testing:MemoziaTests/LLMTitleGenerationTests` 运行；仅发送合成文本。
- 不在文档维护测试数量或“永久通过”结论；以当前源码及实际执行结果为准。
- `ProcessingReliabilityTests` 覆盖跨条目待办、镜像落盘、图片替换、录音写队列与任务引用释放。单独运行此套件并设置 `TEST_RUNNER_MEMOZIA_VERIFY_RECOVERY=1` 可以实际消费临时目录内的后台队列；加密用例使用 `TEST_RUNNER_MEMOZIA_EPHEMERAL_TEST_ENCRYPTION=1`。
- `python3 Scripts/runtime_verify/benchmark_long_transcript.py <Memozia 可执行文件>` 在临时持久库中做首次与重复对账，逐次核对 3,000 个片段的归属。主线程最长延迟默认须低于 50 毫秒，可通过 `Memozia_MAINBLOCK_THRESHOLD_MS` 调整。此基准已纳入 `run_all.sh`。
- `RecordingMergeTests` 用真实音频检查拼接顺序、不同采样率、转写偏移、待办与镜像保留、目录原子交换/回滚及失败不删原件。测试可设置 `TEST_RUNNER_MEMOZIA_EPHEMERAL_TEST_ENCRYPTION=1` 使用进程内随机测试密钥（仅 Debug 测试宿主生效，不访问用户 Keychain）；密文测试产物只适用于该进程。完整合并/删除/磁盘对账用例另需 `TEST_RUNNER_MEMOZIA_VERIFY_RECORDING_MERGE=1`，必须以 `-only-testing:MemoziaTests/RecordingMergeTests` 单独运行，避免异步存储根覆盖影响其他 suite。
- 类型检查不覆盖链接、签名和运行时；音频设备、权限、Keychain、窗口、恢复及 worker 需按 [回归场景](../TECH_DEBT.md) 选择实测。

## 6. SDK 兼容经验

- AudioConverter 在 macOS 26+ 使用 provider/receiver 异步路径，保留旧系统 Reader/Writer 实现。
- SystemAudioCaptureService 的新实时写入路径使用 SampleBufferReceiver；MicCaptureService 的 macOS 27+ 路径使用只读 tap。
- 新 API 通过 availability 分支接入，不能为消除弃用警告提高应用最低部署版本。
- `deploymentTarget` 是当前工程使用的键；旧错误键 `deploymentTargets` 曾导致最低系统版本未正确生成。

## 7. 调试与常见问题

| 场景 | 入口 |
|---|---|
| 分离阈值校准 | 应用可执行文件 `--calibrate-diarization <音频> [阈值或 centroid/refine 模式] [模型目录]`；参数以 DiarizationCalibrator 为准 |
| worker 调试 | 应用可执行文件 `--background-worker` 会真实消费持久队列，仅对隔离测试数据使用；协议见架构 §3 |
| 提醒事项 URL | `reminders_url_diagnostic` 偏好控制 RemindersURLDiagnostic；诊断文件不作为常驻上下文 |
| 长录音保存失败 | 检查句柄数、磁盘和 PersistenceReporting 日志；启动 fd 限制提升见 ProcessLimits |
| 系统音频无声 | 检查系统录音权限、声音输出设备和首包 host time |
| 热键/语言不生效 | 检查用户热键配置、系统冲突；语言设置写 AppleLanguages 后重启 |
| TCC 调试 | 仅明确的开发排障使用 DEBUG 清理路径，不在发布版自动重置授权 |

## 8. GitHub 安全检查

[安全扫描工作流](../../.github/workflows/codeql.yml) 在默认分支推送、PR、每周定时及手动触发时运行：CodeQL 分析 Python 与 GitHub Actions；Swift/Objective-C 源码由 mobsfscan 进行安全模式检查，结果以 SARIF 发布到仓库的 **Security and quality → Code scanning**。mobsfscan 是固定提交的 LGPL-3.0 开源 CI 工具，其依赖由上游锁文件安装，不随应用分发，不增加安装包体积；规则检查不能等同于编译跟踪或完整数据流分析。解析不完整的文件会在运行摘要、注解和 SARIF 中标明覆盖缺口；执行错误会让任务失败。

GitHub 当前[不支持 macOS 27 / Xcode 27 的 CodeQL 构建跟踪](https://github.blog/changelog/2026-10-19-codeql-changes-for-macos-27-xcode-27-and-swift-6-4/)，因此没有为扫描降低应用所需的 SDK，也不将 Swift 规则检查标作 CodeQL 分析。应用的构建与 `Verify Embedded Frameworks` 继续由 CI 和发布流程执行。

[Swift 规则配置](../../.github/mobsf.yml) 排除与 macOS 开源桌面项目无关的移动端键盘、越狱及反逆向控制。凭据、随机数与传输安全规则保留；单条误报须结合源码和系统 API 文档核对，并在 GitHub 告警中记录理由。

Dependabot 漏洞告警读取已提交的 `Package.resolved` 与工作流依赖。[Dependabot 配置](../../.github/dependabot.yml) 每周为 GitHub Actions 依赖提出更新 PR；SPM 依赖继续通过 `project.yml`、XcodeGen 和依赖锁文件的现有流程更新。自动检查与告警不等于完成漏洞修复或人工安全审计。
